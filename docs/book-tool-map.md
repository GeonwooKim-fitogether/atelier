# 묶음 1 — 1장이 정한 것

## 01단계 = 1장 사용자 중심 기획

책 1장은 도구 하나를 정하는 장이 아니라 **기획 전체의 사고 틀**을 정하는 장이다. 여기서 나온 것 네 가지가 이후 모든 단계의 바탕이 된다.

### 사용자 관찰 5요소 — 정본 01단계 "5축"의 출처

책은 "사용자가 무엇을 필요로 하는지 파악하는 가장 확실한 방법은 관찰하는 것"이라 하고, 관찰할 때 기준으로 잡을 다섯 가지를 정해 두었다.

| 요소 | 뜻 |
|---|---|
| **맥락** (context) | 사용자가 제품·서비스를 사용하는 시간, 장소, 상황, 사회 문화적 환경 |
| **행동** (behavior) | 사용자가 제품·서비스와 상호 작용하는 방식 |
| **니즈** (needs) | 사용자의 내적 욕구 |
| **태도** (attitude) | 사용자의 제품·서비스에 갖는 인지적·정서적 반응 |
| **동기** (motivation) | 사용자로 하여금 어떤 행동을 하게 하는 요인 |

정본 `01-intake.md`가 쓰는 5축(맥락·행동·필요·태도·동기)이 바로 이것이다. **출처가 확인됐다.**

책이 이 다섯을 정한 이유도 함께 적어 둔다. 헨리 포드의 말 — "만약 사람들에게 무엇을 원하느냐고 물었다면, 그들은 더 빠른 말을 원한다고 말했을 것이다." 사용자는 자신의 니즈를 명확히 인식하지 못하고 피상적으로 표현하는 경향이 있으므로, **묻는 것보다 관찰하는 것**이 확실하다는 것이다.

### 5 whys — 근본 원인 파고들기

처음 발견한 문제 현상에 "그래서?", "그게 왜 발생했는데?"를 반복해 가장 깊은 곳까지 파고든다. 정본 `01-intake.md`가 이미 쓰고 있다.

### 프로덕트 핏과 마켓 핏 — 둘은 다른 것이고 둘 다 검증해야 한다

이것이 1장에서 가장 중요한 구분이다.

| | 묻는 것 |
|---|---|
| **프로덕트 핏** (product fit) | 우리 제품이 사용자의 문제를 **해결해 주는가** |
| **마켓 핏** (market fit) | 이 제품에 **돈을 지불할** 사용자가 충분한가 |

책이 못 박는 문장: **"보통 많은 제품·서비스가 프로덕트 핏만 있고 마켓 핏까지는 검증하지 못해 지속적인 운영을 하지 못하는 경우가 많습니다."** 근거로 CB 인사이트의 스타트업 실패 원인 조사를 든다 — 1위가 **시장 니즈 없음 42%**로, 팀 문제(23%)나 경쟁 심화보다 앞선다.

린 제품 개발 과정은 여섯 층 피라미드로 그려진다. 아래 두 층(1. 타깃 사용자, 2. 사용자 니즈)이 **마켓**이고, 위 네 층(3. 가치 제안, 4. 피처 셋, 5. UX, 6. 사용자를 통한 검증)이 **프로덕트**다. 둘이 맞닿는 자리가 프로덕트-마켓 핏이며, 6층에서 다시 1층으로 되돌아가는 점선이 그려져 있다.

### 더블 다이아몬드 — 묶음 구조의 원형

| 단계 | 하는 일 |
|---|---|
| **발견** (discover) | 사용자를 관찰하고 비즈니스 목표를 파악한 뒤 이해관계자 의견을 듣는다. **4단계 중 가장 중요** |
| **정의** (define) | 문제를 정의하고 데이터를 종합해 인사이트를 발견한다. 두 다이아몬드가 맞닿는 이 지점이 **전체 프로젝트의 방향성과 전략을 정하는 자리** |
| **발전** (develop) | 와이어프레임과 프로토타입으로 솔루션을 시각화·구체화한다 |
| **전달** (deliver) | 사용성 테스트로 제품을 개선한다 |

첫 다이아몬드가 문제를 찾고 정의하는 과정, 두 번째가 문제를 해결하는 과정이다. atelier의 5 묶음 구조가 이것과 대응한다.

### 문제를 일찍 정의해야 하는 이유

책은 그래프로 보여 준다. 프로젝트 정의에서 출시로 갈수록 **디자인 대안의 개수는 줄고 수정에 드는 비용은 급격히 오른다.** 그래서 문제를 초기부터 정확하게 정의하는 것이 좋다.

# 묶음 2 — 2장과 3장이 정한 것

## 02단계 = 2장 성공하는 제품을 위한 리서치

### 이해관계자 인터뷰 — 질문의 범위를 셋으로 나눈다

| 범위 | 질문 |
|---|---|
| **비즈니스** | 프로젝트의 성공을 어떻게 정의하고 있나 / 핵심 성과지표(KPI)가 있나 / 어떤 사업적 기회가 있나 / 비즈니스적·기술적·사업적 제약은 없나 |
| **경쟁자** | 경쟁 서비스는 어떤 것이 있나 / 경쟁사와 비교하여 더 나은 점(차별점)은 무엇인가 |
| **사용자** | 사용자는 누구고 어떤 특성(행동·상황)을 가지고 있나 / 사용자의 목표는 무엇이고 목표 달성에 어떤 어려움이 있나 / 사용자가 우리 서비스에 관심을 가지는 이유는 / 궁극적으로 제공하고자 하는 가치는 / 사용자에 대해 어떤 가설을 가지고 있나 / 지금까지 해온 시도 중 실패한 것과 성공한 것은 / 사용자가 어떻게 행동하기를 바라나 / 그 행동은 우리 비즈니스와 어떤 연관이 있나 |

### 포지셔닝 맵 (p56)

경쟁사의 제품·서비스가 시장에서 차지하는 위치를 시각적으로 한눈에 보고, 우리가 나아가야 할 방향의 단서를 찾는다. 책의 Tip: **"타깃 시장과 방향성에 따라 축은 달라질 수 있습니다."** 예시에서는 원의 크기와 색으로 정보를 더 실었다.

### 경쟁 분석표 (p57)

**보통 3~5개**의 제품·서비스를 표로 비교한다. 가장 보편적으로는 **피처를 세로로 나열하고 경쟁사가 그 피처를 가지고 있는지**를 Yes(초록 점)·No(빨강 점)로 표시한다. 책의 Tip: **"단순히 피처 유무 외에 피처의 수준을 비교하기도 합니다."**

### 심층 인터뷰 — 다섯 단계

타깃 사용자 **3~5명**과 직접 대면하며, 보통 한 패널당 **30~60분**이 걸린다.

1. **인터뷰 대상자 선정** — 기준은 "제품·서비스에 대한 태도 및 이용 특성" 또는/그리고 "제품·서비스의 주제와 연관성"에, "인구통계학적 기준"을 더한다.
2. **이슈 리스트 작성** — 질문을 중구난방으로 내지 않도록 **사용자 · 맥락 · 동기 · 제품/서비스의 특성 · 행동** 다섯 가지를 카테고리로 잡는다.
3. **인터뷰 질문 설계**
4. **대상자 모집**
5. **인터뷰 진행**

진행 원칙도 정해져 있다. 단답·피상적 답변이 나오지 않도록 **꼬리의 꼬리를 무는 방식**으로 묻고, **답변 범위가 넓은 질문에서 구체적인 질문으로 좁혀** 간다. 특정 답변을 기대하거나 그렇게 느낄 수 있는 질문은 피한다(나쁜 예: "제품의 ○○ 기능을 문제라고 느낀 적은 없나요?"). 범위가 너무 넓은 질문도 피한다(나쁜 예: "구글에 대해서 어떻게 생각하세요?" / 좋은 예: "가장 최근에 스트리밍 서비스를 이용한 게 언제인가요?").

### 그 밖의 정성 리서치 세 가지

| 방법 | 무엇인가 |
|---|---|
| **포커스 그룹 인터뷰** | 소수의 참여자를 모아 자유롭게 대화하게 하고 그 과정에서 정보를 얻는다. 일부 참여자에게 편향되지 않도록 진행자가 중재해야 한다 |
| **맥락 관찰** (contextual inquiry) | 사용자에게 특정 환경에서 특정 과업을 하도록 요청한 뒤 행동 패턴·반응을 관찰한다. 의사·변호사·엔지니어처럼 현장 경험이 중요하거나 전문적이어서 단순 인터뷰로 맥락을 파악하기 어려울 때 유용하다 |
| **오즈의 마법사** (wizard of oz) | 참가자가 시스템인 척하는 관찰자와 상호 작용하게 한다. 복잡한 제품을 개발하기 전에 사용자가 어떤 형태로 상호 작용하는지 관찰할 수 있다 |

## 03단계 = 3장 인사이트를 분석하는 데이터 모델링

### 어피니티 다이어그램 — 네 단계와 세 가지 색

리서치에서 수집한 데이터를 정리·가공하는 과정을 **데이터 모델링**이라 하고, 실무에서 가장 많이 쓰는 방법이 어피니티 다이어그램이다. 준비물은 수집한 데이터와 **세 가지 색(노란색·파란색·분홍색)의 포스트잇**이다.

| 단계 | 무엇을 하나 | 색 |
|---|---|---|
| 1 | **어피니티 노트 작성** — 유의미한 데이터를 선별해 적는다. **하나의 노트에 하나의 데이터.** 다른 사람도 이해할 수 있도록 구체적이고 쉽게 | 노란색 |
| 2 | **그룹화** — 공통되거나 비슷한 노트를 묶는다. 분류하면서 새 패턴이나 아이디어가 떠오르면 함께 기록한다 | — |
| 3 | **상위 헤더 작성** — 각 그룹을 대표하는 문장. 요약이 아니라 **그룹 내 노트들을 아우르는 문장**으로 쓴다 | 파란색 |
| 4 | **최상위 헤더 작성** — 파란 헤더들을 여러 조합으로 연결해 가설을 도출한다. 이것이 **키 인사이트**이며 솔루션의 전략과 방향성을 세우는 데 결정적이다 | 분홍색 |

**이 4단계가 04단계와 이어진다.** 4장 4-1이 "어피니티 다이어그램의 **최상위 헤더를 질문으로 전환**해 HMW를 만든다"고 하기 때문이다. 즉 HMW는 아무 데서나 나오는 것이 아니라 **분홍색 최상위 헤더에서 나온다.**

### 퍼소나 — 어피니티 인사이트 위에 세운다

퍼소나는 어피니티 다이어그램과 같은 데이터 모델링 방법의 하나로, 앨런 쿠퍼가 처음 제안했다. 책이 못 박는 두 가지가 있다.

1. **퍼소나는 어피니티 다이어그램에서 발견한 인사이트를 중심으로 구성해야 한다.** 가상 인물이지만 실제 사용자에게서 얻은 데이터가 바탕이어야 한다.
2. 사용자별 성향이 명백히 다르거나 플랫폼 서비스를 운영한다면 **둘 이상의 퍼소나**를 정의하고, 여러 개일 때는 **퍼소나의 우선순위**를 정한다.

퍼소나 한 장은 여섯 블록으로 구성된다(p081 실습 템플릿) — **기본 소개 / 행동 변수 / 행동·맥락 / 불편한 점(Pain Points) / 목표·니즈 / 필요한 기능**. 정본 `03-analysis.md`가 "책 6 block 정합(3장 81p)"이라 적은 것이 이것이며, **일치가 확인됐다.**

## 05단계 = 4-2 피처 우선순위 + 4-3 솔루션의 방향성

| 도구 | 책이 정한 서식 |
|---|---|
| **2×2 매트릭스** | 가로축 = **필요한 자원**(왼쪽 많이 듦 / 오른쪽 적게 듦), 세로축 = **사용자에게 제공할 가치의 크기**. 사분면 칸에 나눠 담는 것이 아니라 **그래프 위에 피처를 배치**하고, **오른쪽 상단 끝에 가까운 피처부터** 만든다. 자원 산정은 **개발자와 함께** |
| **As is / To be** | 왼쪽 As is 쪽이 **사용자 · 맥락 · 불편 사항/니즈** 세 칸, 화살표 건너 오른쪽에 **피처**. 행마다 누구의 이야기인지가 먼저 온다 |
| **방향성 문장** | "사용자(퍼소나)들이 [ ]한 상황(맥락)에서 [ ]한 문제(불편 사항/니즈)를 겪고 있기 때문에, [ ]한 기능(피처)들이 필요하다." |

# 묶음 4·5 — 5장이 정한 것 (아직 착수 안 함)

정본 스킬(`atelier-npi/SKILL.md`)은 Stage 06~09를 **"미구축"** 으로 비워 두었다. 그런데 책 5장이 그 자리를 이미 채워 놓았다. **묶음 4·5는 새로 설계할 것이 아니라 아래를 옮겨 오면 된다.**

## 06 서비스 설계

### 5-1 유저 스토리 — 걸킨(Gherkin) 템플릿

책은 유저 스토리 하나를 **네 부분**으로 정해 두었다.

| 부분 | 무엇을 적나 |
|---|---|
| ① **제목** (title) | "〈사용자〉는 〈작업〉을 할 수 있다." 형식의 한 문장. **오른쪽 상단에 우선순위(상·중·하)** 를 함께 표시한다 |
| ② **유저 스토리** (background) | **AS** 사용자 / **I WANT** 사용자의 행동(피처) / **SO THAT** 그것을 함으로써 얻는 이득(니즈·목적) |
| ③ **구현에 대한 기준** (acceptance criteria) | **Given** 주어진 상황 / **When** 조건 및 행동 / **Then** 결과. **한 문장에 하나의 행동**만 담고, 추가 행동은 `and`로 잇는다. `or`는 분기에만 쓴다 |
| ④ **비고** (notes) | 팀원이 알아야 할 사항 — 디자인 링크, 이전에 내린 결정 사항 등 |

유저 스토리들이 모이면 **백로그**가 되고, 그중 이번에 개발할 것을 골라 **스프린트**로 묶는다.

### 5-4 백 오피스 기획

- 백 오피스는 사용자가 직접 보는 화면이 아니지만, **사용자가 늘면 운영 측면에서 차이가 크게 벌어진다.**
- 화려한 디자인보다 **정보 구조와 가독성**을 우선한다.
- 가장 중요한 지침: **데이터가 전무한 시점부터** 데이터가 생성되고 사용자와 인터랙션하는 **전체 고객 여정 지도**를 그려 보면 어떤 피처가 필요한지 빠짐없이 챙길 수 있다. 데이터가 이미 있다고 가정하고 사용자 화면부터 그리면 다양한 상황에 대응하기 어렵다.
- 초기에는 지나치게 복잡하게 설계하지 말고 대략적 구조를 잡은 뒤 개발자와 주고받으며 다듬는다.

### 5-5 정보 구조 (IA, Information Architecture)

- 정보 구조란 정보의 성격·순서·우선순위에 따라 구조화하는 것이다. 잘 설계하면 사용자가 **스스로 길을 찾는다**.
- 기준은 **멘탈 모델** — "비밀번호 변경은 [내 정보]에 있을 것이다" 같은 직관적 흐름을 그대로 따라가게 만든다.
- 웹은 홈에서 시작해 계층으로 내려가는 **사이트 맵**, 앱은 **하단 탭이 최상위 레벨**에 오고 그 아래 계층이 붙는다.
- 실무에서는 **구글 스프레드시트의 열로 계층을 표현**하는 방법을 자주 쓴다.
- 메뉴를 어떻게 묶을지는 **카드 소팅**(사용자가 직접 카드의 우선순위를 세우고 그룹화하는 정성 리서치)으로 정한다.

**내비게이션 세 유형**

| 유형 | 구조 | 어디서 보나 |
|---|---|---|
| **계층적** | 홈에서 한 계층씩 아래로. 연결되지 않은 페이지로 가려면 처음 화면으로 돌아가야 한다 | 이메일 서비스, 기업 페이지, 폴더 구조 |
| **플랫** | 최상위 메뉴가 2개 이상이고 서로 이동 가능. 안드로이드는 보텀 내비게이션, iOS는 탭 바 | 인스타그램 등 대부분의 앱 |
| **콘텐츠 드리븐** | 콘텐츠에서 콘텐츠로 이동. 콘텐츠 자체가 내비게이션을 결정한다 | 게임, 전자책 |

## 07 시제품 만들기 = 5-2 유저 플로 & 와이어프레임

**순서가 정해져 있다 — 유저 스토리 → 유저 플로 → 와이어프레임.** 책은 이 셋을 세로로 배치해 한눈에 보는 것을 "연습하는 가장 좋은 방법"으로 든다.

### 사용자 여정 지도 (User Journey Map)

가로는 단계(유입 → 회원가입 → 탐색 → 주요 과제 …), 세로는 네 줄이다.

| 줄 | 내용 |
|---|---|
| 유저 스토리 | 그 단계에서 사용자가 하는 일 |
| Emotions | 만족도 곡선. 가장 높은 지점이 **아하 모먼트** |
| 니즈 & 불편한 점 | 그 단계에서 느끼는 것 |
| 필요한 피처 | 그것을 해결할 피처 |

**예측으로 작성하면 안 된다 — 리서치 데이터를 기반으로 한다.**

### 태스크 플로와 유저 플로

| | 무엇을 그리나 |
|---|---|
| **태스크 플로** | 분기와 오류 없이 큰 그림만. 전체 흐름을 먼저 잡을 때 |
| **유저 플로** | 분기·오류·필요 사항까지. 실제 설계용 |

**기호 세 가지**: 둥근 사각형은 시작과 끝, 직사각형은 동작·프로세스, 마름모는 조건·분기.

**복잡한 플로의 색 규칙**: 파란색은 사용자가 위치한 페이지, 초록색은 모달 창, 주황색은 사용자 행동(클릭·입력), 빨간색은 시스템 행동(메일 발송·푸시).

### 와이어프레임

- **로우 피델리티 → 하이 피델리티** 순서. 로우에서는 시각적 충실도를 낮추되 **요소들의 위치와 피처의 흐름은 모두 잡아야** 한다.
- 와이어프레임을 다 그린 뒤 **그 아래에 해당 기능에 대한 설명**을 간단히 적는다.
- 도구: 발사믹(스케치 느낌의 로우 피델리티), 오븐(카카오, 무료), 피그마(인터랙션까지 넣어 실제 사용자 테스트 수준의 프로토타입 가능).

## 08 검증 = 5-6 QA와 테스트 케이스

### QA 프로세스 (1~2 스프린트마다)

QA 환경 배포 → 1차 테스트 및 오류 수정(**테스트 케이스** 참조) → 스테이징 환경 배포 → 최종 확인 및 배포 → **스모크 테스트**.

### 테스트 케이스 표 — 아홉 열

`No · 테스트 시나리오 · 테스트 조건 · 실행 순서 · Pass Result · 테스트 환경 · P/F · 실제 결과 · 비고`

- **테스트 시나리오**에는 테스트할 피처를 적는다. 유저 스토리의 "~을 할 수 있다"를 그대로 써도 된다.
- **실행 순서**와 **Pass Result**에는 유저 스토리의 "구현에 대한 기준"(Given/When/Then)을 반영한다.
- **테스트 환경**은 웹이면 모바일·데스크톱·브라우저, 앱이면 운영체제·기기·해상도.
- 작성은 **대분류에서 하분류로 범위를 좁히면서** 한다.

**P/F 값 다섯 가지**

| 값 | 뜻 |
|---|---|
| Pass | 정상 작동 |
| Fail | 비정상 작동으로 이슈 발생 |
| Block | 여러 원인으로 테스트 진행이 보류 |
| N/A (Not Available) | 개발이 지연·취소된 기능, 또는 협의해서 테스트를 진행하지 않는 경우 |
| N/T (Not Tested) | 아직 테스트를 진행하지 않은 경우 |

**테스트 케이스는 100% 통과를 목표로 하지 않는다.** 부족한 부분이 있을 가능성을 두고 협업으로 보완해 나간다.

### 테스트 유형의 우선순위

책은 역삼각형으로 그린다 — 위가 우선순위 높음.

| 순위 | 유형 | 무엇을 보나 |
|---|---|---|
| 1 | **스모크 테스트** | 회원가입·로그인·결제 등 주요 플로가 도는지 |
| 2 | **해피 패스 테스트** | 가장 일반적인 사용자 여정 |
| 3 | **리그레션 테스트** | 이전에 버그로 보고됐던 이슈가 되살아났는지 |
| 4 | **엣지 케이스** | 주요 플로 밖의 예외. 리소스 여유가 있을 때 |

**소규모·애자일 조직은 탐색적 테스팅으로 대체하기도 한다** — 테스트 케이스를 미리 쓰지 않고 1~2시간으로 시간을 제한해 바로 돌려 보고 요약 보고하는 방식이다. 공방장 1인 체제에는 이쪽이 현실적이다.

## 09 인계 자료 묶기 = 5-3 서비스 기획서

### 기획서가 왜 필요한가

애자일이 퍼지며 파워포인트 기획서가 간소화되고 피그마에서 바로 협업하는 경우가 늘었다. 그러나 **개발자 입장에서는 디자인만으로 상세 기능이나 의도를 파악하기 어렵다.** 그래서 기획서는 "소통을 위한 문서"이고, 도구가 무엇이냐는 중요하지 않다. 화면 설계서·스펙 문서·스토리보드 등으로 불린다.

### 기획서 한 장의 구조

| 자리 | 무엇이 오나 |
|---|---|
| 상단 | **페이지 혹은 플로 이름** |
| 가운데 | **와이어프레임** — 스크린들의 흐름 위주. 각 요소를 화살표로 연결. 문서에 넣는 와이어프레임은 **로우 피델리티인 경우가 많다** |
| 오른쪽 또는 하단 여백 | **세부 기능 및 특정 상황에서의 로직** — 컴포넌트 단위로("Text field_이름 — 실시간 등록 확인", "Button_인증 — 인증 번호 Validation") |

### 에러 케이스

특정 플로나 피처에서 발생할 수 있는 오류와 그 대응을 정리한 문서다. 개발 오류뿐 아니라 **사용자가 설계한 의도와 다르게 행동하는 것**, 기획자가 미처 고려하지 못한 접근까지 포함한다.

표는 두 열이다 — **Error Cases · Wording**. 에러 케이스만 적는 것이 아니라 **그때 사용자에게 띄울 문구를 함께** 정리한다. 한쪽에는 와이어프레임, 다른 쪽에는 그 흐름에서 나올 수 있는 에러 케이스를 모두 적는다.
