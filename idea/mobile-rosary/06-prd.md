# 제품 요구사항 (PRD) — mobile-rosary V1

> 한 줄 요지: **05단계는 "무엇을 첫 판에 넣을까"까지만 정했다. 이 문서는 그것을 "만들 수 있는 것"으로 바꾼다** — 기능마다 규칙과 예외를 못 박고, 같은 일을 경쟁자가 어떻게 푸는지 화면 단위로 대조해 **우리 차이가 진짜 USP인지 판정**한다.

06단계는 세 산출물로 이뤄진다. 이 문서가 첫째다.

| | 산출물 | 무엇을 정하나 |
|---|---|---|
| **06-a** | **이 문서 (PRD)** | 기능 요구사항 · 기능 단위 경쟁 대조 · USP 확정 · 비기능 요구사항 · 데이터 · 엣지 케이스 · 범위 밖 |
| 06-b | [`06-design-system.md`](./06-design-system.md) | 색·서체·컴포넌트·모션·접근성·톤 |
| 06-c | [`06-service-design.md`](./06-service-design.md) | 유저 스토리(걸킨) · 정보 구조 · 백 오피스 판단 |

**왜 이 문서가 새로 생겼나.** 2026-08-28까지 이 파이프라인에는 "화면 수준의 경쟁 분석"이 없었다. 03단계가 시장 수준 경쟁 분석(회사 규모·가격·포지셔닝)을 하고 끝났고, 그다음은 곧바로 만들기였다. 그 결과 USP가 **"한국어 + 손 없이"라는 슬로건**으로만 존재하고 **화면 어디에서 그것이 드러나는지**가 정해지지 않았다. 슬로건은 앱스토어 소개문에는 쓸 수 있지만 개발자에게 넘길 수는 없다.

---

## 0. 이 제품이 무엇인가 — 정의를 먼저 못 박는다

**이 절은 2026-08-30에 신설했다.** 신설 사유가 이 파이프라인의 결함 하나를 드러내므로 먼저 적는다.

01단계는 통증을 모았고, 02는 경쟁자가 못 하는 것을 찾았고, 03은 빈자리를 짚었고, 04는 그 빈자리를 메울 아이디어를 냈고, 05는 그중 셋을 골랐다. **그런데 어디에도 "그래서 이 제품은 무엇인가"를 정하는 자리가 없었다.** 그 결과 05가 06에 물려준 것은 **차별 기능 셋뿐**이었고, 앱의 골격에 해당하는 것들 — 오늘의 신비, 71단계 핵심 루프, 완주 화면, 지금 몇 번째 알인지 — 은 PRD를 쓰다가 **그 자리에서 발명됐다.** 실측으로 확인했다: "오늘의 신비", "71", "완주 화면" 이라는 말이 01~05 문서에 한 번도 나오지 않는다.

차별점만 물려받으면 **차별점의 목록**이 나오지 제품이 나오지 않는다. 그래서 이 절이 제품 전체를 먼저 세우고, 그다음에 차별점이 그 위 어디에 얹히는지를 말한다.

### 0-1. 이 제품의 정체

> **묵주기도 한 번을 처음부터 끝까지 함께 바쳐 주는 앱.**

파는 것은 기능 목록이 아니라 **한 번의 완주**다. 그래서 성공은 "기능이 다 있다"가 아니라 **"오늘 5단을 마쳤다"** 로 잰다.

### 0-2. 핵심 루프 — 이 앱이 하는 일의 전부

묵주기도 한 번은 **71단계**로 이뤄진다. 시작 기도 여섯 단계와, 다섯 단 각 열세 단계다.

```
시작 기도 (6단계)
  십자가 성호 → 사도신경 → 주님의 기도 → 성모송 ×3 → 영광송
    ↓
제1단 ~ 제5단 (각 13단계 = 65단계)
  신비 선포 → 주님의 기도 → 성모송 ×10 → 영광송 → 구원을 비는 기도
    ↓
마침 기도 → 완주
```

이 71단계를 순서대로 넘기는 것이 앱의 **핵심 루프**이며, 화면의 90%는 이 루프를 위해 존재한다. 다른 모든 기능은 이 루프의 **앞(시작하기)** 이나 **뒤(이어가기·마치기)** 에 붙는다.

### 0-3. 제품의 뼈대 — 이것들은 차별점이 아니라 제품 그 자체다

아래는 "있으면 좋은 것"이 아니라 **없으면 묵주기도 앱이 아닌 것**이다. 앞서 이것들이 PRD 집필 중 즉석으로 나왔던 것을 여기서 정식 항목으로 올린다.

| 뼈대 | 왜 제품 그 자체인가 |
|---|---|
| **오늘의 신비** | 묵주기도는 요일마다 묵상 대상이 다르다. 이것 없이는 무엇을 바칠지 정할 수 없다 |
| **71단계 순서 진행** | 기도의 형식 자체다 |
| **지금 어디인가** | 쉰 번을 세는 기도이므로 위치를 잃으면 기도가 끊긴다 |
| **마침** | 시작이 있으면 끝이 있어야 한다. 끝이 없으면 완주 여부를 알 수 없다 |
| **지향** | 묵주기도는 누군가를 위해 바치는 기도다. 대상 없는 묵주기도는 형식만 남는다 |

### 0-4. 그 위에 차별점이 얹힌다

뼈대는 경쟁자도 갖고 있다(조사 §4-3 기본 요건). 우리 차별점은 **그 뼈대의 특정 자리에 얹히는 것**이지 뼈대를 대체하는 것이 아니다.

| 뼈대의 어느 자리 | 얹히는 차별점 |
|---|---|
| 71단계를 넘기는 방식 | **교대 낭송** — 앱이 앞 절, 사용자가 뒷 절 |
| 지금 어디인가를 보이는 방식 | **실제 묵주 형태 + 숨 쉬는 현재 알** |
| 화면의 배경 | **한국 성화의 성모님** |
| 화면의 색 | **전례 시기를 따라 바뀐다** |
| 끊겼을 때 | **자동 저장, 그 자리부터** |

**이 표가 이 문서의 설계 원리다.** 아래 모든 요구사항은 왼쪽 칸(뼈대)이거나 오른쪽 칸(차별점)이며, 둘 다 아닌 것은 V1에 넣지 않는다.

### 0-5. 우리가 지나간 갈림길 — "완주"를 누가 하는가

**이 항목은 프랑스 앱 Rosario의 실화면을 보고 신설했다(조사 §1-4).** 같은 통증에 정반대의 답이 존재한다는 것을 그때까지 몰랐기 때문이다.

우리가 01단계에서 잡은 통증은 **"혼자서 5단을 끝까지 못 간다"** 였다. 여기서 답이 두 갈래로 갈린다.

| | 우리의 답 | Rosario의 답 |
|---|---|---|
| 해법 | 끊겨도 그날 안에 이어 붙여 **혼자 완주한다** | **5단을 다 하지 마라.** 다섯 명이 한 단씩 맡아 조 전체가 한 바퀴를 채운다 |
| 완주의 주체 | 개인 | 조(5인) |
| 하루 분량 | 5단 (약 20분) | 1단 (5분) |
| 필요한 것 | 없음 | 계정 · 서버 · 조 편성 · 진행 동기화 |

**우리가 왼쪽을 택한 이유는 취향이 아니라 이미 정해진 제약이다.** §4 비기능 요구사항이 *"지향에는 아픈 사람의 이름이 들어가므로 기기 밖으로 나가는 데이터가 없다"* 를 못 박고 있다. 오른쪽 길은 서버와 계정 없이는 성립하지 않는다. 즉 우리는 **조 기반 기능 전체를 대가로 지불하고 개인의 사생활을 택했다.**

이 선택은 되돌릴 수 있으나 되돌리는 값이 크다(서버·계정·동기화가 통째로 생긴다). 그러므로 V1에서는 왼쪽 길로 끝까지 가고, 조 기반 기도는 [§6 범위 밖](#6-v1-범위-밖--만들지-않는-것)의 "가족 계정·본당" 항목에 흡수한다.

## 1. 이 제품이 파는 것 — 한 문장

> **묵주와 기도문 없이, 화면을 보지 않고, 끊겨도 그날 안에 5단을 마칠 수 있는 한국어 묵주기도 앱.**

05단계 방향성 문장의 압축이며, 아래 모든 요구사항은 이 문장을 더 잘 되게 하는지로 평가한다. 이 문장을 더 낫게 하지 않는 기능 제안은 V1에서 뺀다.

---

## 2. 기능 단위 경쟁 대조 — USP는 여기서 만들어진다

**규칙 하나를 먼저 못 박는다. 다른 것이 전부 USP는 아니다.** 사용자가 **그 차이 때문에 우리를 고를 때만** USP다. 그렇지 않은 차이는 그냥 취향이거나, 더 나쁘게는 남들이 안 하는 데 이유가 있는 것이다. 그래서 마지막 두 칸이 이 표의 핵심이다.

근거는 03단계 피처 매트릭스(7 경쟁자 × 19 피처)와 02단계 조사다. **직접 써 보지 못해 모르는 것은 "미확인"으로 적는다** — 추측을 사실처럼 적지 않는다.

### 2-1. 기도를 시작하는 방법

| | 어떻게 하나 |
|---|---|
| Hallow | 앱을 열고 콘텐츠 목록에서 묵주기도를 고른 뒤 재생. 통합 패키지라 묵주기도까지 여러 단계 |

| 한국 앱 (성모님·굿뉴스) | 앱을 열고 메뉴에서 고른다. UX 투박 (03 실측) |
| **우리 V1** | 앱을 열면 **시작 단추 하나.** 이어가기가 있으면 그 위에 카드 하나 |
| **차이** | Marcello와 거의 같다. Hallow보다 짧다 |
| **USP인가** | **아니다.** ① 한마디로 시작(음성)이 0표를 받은 것이 이를 뒷받침한다 — 01단계 다섯 마찰 어디에도 "시작이 번거롭다"가 없다. **여기서 이기려 하지 않는다. 지지 않기만 하면 된다.** |

| Marcello | 화면의 묵주 알을 **손으로 탭**해 넘긴다 |

| **차이** | 한국어로 이것을 하는 앱이 없다 (03 피처 매트릭스에서 "AirPods hands-free" 행이 전부 ○ 또는 ◐) |

### 2-3. 누가 기도문을 읽나 — 가장 큰 차이

| | 어떻게 하나 |
|---|---|
| Hallow | **앱이 전부 읽는다.** 셀럽 목소리가 강점. 사용자는 듣는다 |
| Marcello | 읽어 주지 않는다. 사용자가 전부 바친다 |
| 한국 앱 | 신비 음원 제공. 전부 읽어 주는 방식 (03: 성모님·굿뉴스 ◐) |
| **우리 V1** | **교대 낭송 — 앱이 앞 절, 사용자가 뒷 절.** 전례의 응답 구조 |
| **차이** | **조사한 어느 앱도 이렇게 하지 않는다.** 전부 "다 읽어 준다" 또는 "안 읽어 준다" 둘 중 하나다 |
| **USP인가** | **그렇다 — 2순위이자 가장 방어하기 쉬운 USP.** 이유가 셋이다. **첫째,** 01단계의 "잡생각으로 집중이 깨진다"를 정면으로 겨냥한다 — 듣기만 하면 딴생각이 들어오지만 받아야 하면 그럴 틈이 준다. **둘째,** 이것은 기능이 아니라 **기도의 방식**이라 베끼기 어렵다. 전례를 이해해야 나오는 설계다. **셋째,** 공방장 닷 보팅 최다 득표(2표)다 |

**여기가 이 제품의 진짜 자리다.** 2-2(hands-free)는 한국어 시장이 비어 있어서 우리 것이지만, 영어권 앱이 한국어를 붙이면 사라진다. 반면 2-3(교대 낭송)은 **경쟁자가 한국어를 붙여도 남는 차이**다.

### 2-7. USP 확정 — 이 표의 결론

**2026-08-30 개정.** 경쟁사 실화면 36장(Hallow·Marcello·Rosario)을 확인한 뒤 다시 세웠다. 개정 내역은 [조사 §4-1](./02b-design-research.md)에 있다.

| 순위 | USP | 누구를 이기나 | 얼마나 방어되나 | 어디서 드러나나 |
|---|---|---|---|---|
| **1** | **교대 낭송** (앱이 앞 절, 내가 뒷 절) | **셋 다.** 세 앱 모두 낭송이 오디오 재생 한 방향이라 "내 차례"라는 상태 자체가 없다 | **가장 높음** — 전례를 이해해야 나오는 설계 | 첫 성모송에서 바로 |
| **2** | **한국 성화의 성모님** | Marcello(서양 성화) · Hallow·Rosario(도상 회피) | **높음** — 흉내 내려면 한국 미술을 이해해야 한다 | 첫 화면에서 즉시 |
| **3** | **전례 시기를 따라 바뀌는 색** | 셋 다. 어느 쪽도 하지 않는다 | 높음 — 가톨릭 내부 지식이 필요하다 | 시기가 바뀔 때. 신자만 알아본다 |
| **4** | 한국어로 손 없이 5단 완주 | 셋 다 | 중간 — 영어권 앱이 한국어를 붙이면 좁아진다 | 첫 사용 30초 안에. 앱스토어 첫 줄 |
| **5** | 끊겨도 그날 안에 이어짐 | Marcello의 "Go to…"보다 자동이다 | 중간 | 두 번째 사용부터. **재방문율로 드러난다** |
| — | ~~평생 1회 결제~~ | — | 낮음. **Rosario·Marcello가 완전 무료다** — 오히려 우리가 불리하다 | 결제 화면 |
| — | ~~앱을 열면 바로 기도~~ | Marcello가 이미 지킨다 | **기본 요건으로 강등** | — |

**화면 설계에 주는 지시.** USP 1과 2는 **처음 30초 안에 겪게** 만든다. USP 3은 **겪을 때까지 설명하지 않는다** — 끊기기 전에 "끊겨도 됩니다"라고 알리면 오히려 끊기라고 권하는 인상이 된다.

## 3. 기능 요구사항

각 요구사항에 `FR-##` 번호를 붙인다. 07 목업과 08 테스트 케이스가 이 번호를 참조한다.

### 3-1. 홈

| # | 요구사항 |
|---|---|
| FR-01 | 앱을 열면 오늘의 신비를 요일에 따라 자동으로 정한다 (월·토 환희 / 화·금 고통 / 수·일 영광 / 목 빛) |
| FR-02 | 저장된 진행이 있으면 **시작 단추보다 위에** 이어가기 카드를 둔다. 없으면 카드 자체가 없다 |
| FR-03 | 이어가기 카드는 어디서 멈췄는지(제N단 M번째 알)와 언제 멈췄는지(방금·N분 전·어제)를 적는다 |
| FR-04 | 지향을 고를 수 있고, 고른 지향의 진행이 이어가기 카드에 반영된다 |
| FR-05 | 지향을 추가할 수 있다. 최대 길이 24자 |
| FR-06 | 침묵 진행을 켜고 끌 수 있으며, 상태가 다음 실행까지 유지된다 |
| FR-07 | 받는 사이를 느리게·보통·빠르게 셋 중에서 고를 수 있고 유지된다 |

### 3-2. 기도 진행

| # | 요구사항 |
|---|---|
| FR-10 | 71단계 전체를 순서대로 진행한다 (시작 기도 6 + 5단 × 13) |
| FR-11 | 소리가 켜져 있으면 앱이 **앞 절만** 읽는다. 뒷 절은 읽지 않는다 |
| FR-12 | 앞 절을 마치면 **받는 사이**만큼 기다린 뒤 자동으로 다음으로 넘어간다 |
| FR-13 | 받는 사이 = (900ms + 뒷 절 글자수 × 132ms) ÷ 속도계수. 소리가 없으면 앞 절 몫을 더한다 |
| FR-14 | 침묵 진행이면 소리를 내지 않고 진동만 쓴다 — 알마다 1회, 단 전환 시 3회 |
| FR-15 | 화면 중앙의 알이 상태를 나타낸다 (읽는 중 / 내 차례 / 침묵 / 단 전환). [디자인 시스템 §4](./06-design-system.md) |
| FR-16 | 지금 몇 번째 알인지, 몇 단째인지를 화면에서 볼 수 있다 |
| FR-17 | **알을 넘길 때마다** 진행 자리를 저장한다 |
| FR-18 | 잠시 멈춤 = 자리를 남기고 홈으로. 여기서 끝내기 = 자리를 지우고 홈으로 |
| FR-19 | 5단을 마치면 완주 화면을 보이고 저장된 자리를 지운다 |
| FR-20 | 기도 중에는 화면이 꺼지지 않게 한다 (지원 기기에 한함) |

### 3-4. 화면의 시각 요구사항 (2026-08-30 신설)

경쟁사 실화면 분석에서 나온 것이며, [디자인 시스템](./06-design-system.md)이 규격을 정한다.

| # | 요구사항 | 출처 |
|---|---|---|
| FR-21 | 알을 **실제 묵주의 형태**로 그린다 — 고리(성모송 50 + 주님의 기도 5)와 아래로 늘어진 십자가·꼬리. 정원 균등 배치를 쓰지 않는다 | 조사 §1-3 나. Marcello가 우리 v3보다 나은 지점 |
| FR-22 | 신비가 바뀌면 **배경 성화가 바뀐다.** 무엇을 묵상하는지가 글자가 아니라 그림으로 전달된다 | 조사 §1-3 바. Marcello에게서 배울 것 |
| FR-23 | **묵주가 성모님의 이목구비를 가리지 않는다.** 눈·코·입 영역에 알이나 십자가가 겹치지 않는다 | 조사 §1-3 마-1. Marcello의 결함 |
| FR-24 | **기도문 영역의 높이가 고정**이다. 기도문 길이가 달라져도 배경 그림이 잘리는 양이 변하지 않는다 | 조사 §1-3 마-2. Marcello의 결함 |
| FR-25 | 전례 시기(대림·사순 / 연중 / 부활·성탄·성모축일 / 성령강림·수난)에 따라 **부 강조색이 바뀐다** | Edge point 3 |
| FR-26 | 알의 지름이 화면 폭의 **8% 이상**이다 | 조사 §1-3 마-6. 퍼소나 B 시니어 |

### 3-5. 각 요구사항이 어디서 왔나 (출처 표기)

**이 표는 §0에서 진단한 결함 — "제품의 뼈대가 근거 없이 즉석 발명됐다" — 을 다시 일으키지 않기 위한 장치다.** 앞으로 FR을 추가할 때는 이 표에 한 줄을 함께 넣는다. 출처를 쓸 수 없는 요구사항은 그 자리에서 발명한 것이므로, 넣기 전에 §0의 뼈대인지 차별점인지부터 판정한다.

| 출처 | 해당 FR |
|---|---|
| **§0-3 제품의 뼈대** (묵주기도 앱이라면 반드시 있는 것) | FR-01 · FR-10 · FR-16 · FR-19 · FR-04 |
| **05단계가 물려준 차별 기능** | FR-11 · FR-12 · FR-13 · FR-14 (교대 낭송) · FR-02 · FR-03 · FR-17 (이어가기) |
| **경쟁사 실화면 분석 (02b)** | FR-21 · FR-22 · FR-23 · FR-24 · FR-25 · FR-26 |
| **접근성·기기 제약** | FR-06 · FR-07 · FR-20 |
| **설계상 파생** (위 항목을 만들면 자동으로 필요해지는 것) | FR-05 · FR-15 · FR-18 |

### 3-3. 오류·예외 (책 5-3 Error Cases 서식)

| 상황 | 앱이 하는 일 | 사용자에게 보이는 말 |
|---|---|---|
| 한국어 음성이 기기에 없다 | 소리 없이 진행하고, 받는 사이에 앞 절 몫을 더한다 | "이 기기에 한국어 음성이 없어 소리 없이 진행됩니다. 진동과 사이는 그대로 동작합니다." |
| 진동을 지원하지 않는다 | 사이만으로 진행한다. 오류를 내지 않는다 | (알리지 않는다 — 조작에 영향이 없다) |
| 기도 중 전화가 온다 | 자리를 저장하고 멈춘다 | (복귀 시 홈의 이어가기 카드로) |
| 저장 공간을 쓸 수 없다 | 진행은 정상, 자리 저장만 실패 | "이 기기에서는 진행 자리를 기억할 수 없습니다." — 한 번만 |
| 지향 이름이 비었다 | 추가하지 않고 시트를 닫는다 | (알리지 않는다) |
| 저장된 자리가 손상됐다 | 자리를 버리고 처음부터로 둔다 | "이어갈 자리를 찾지 못해 처음부터 시작합니다." |

**붉은 경고색을 쓰지 않는다.** 기도 맥락에서 붉은 경고는 벌주는 인상을 준다 ([디자인 시스템 §2](./06-design-system.md)).

## 5. 저장하는 것

서버가 없으므로 전부 기기 안이다.

```
설정          침묵진행(참/거짓) · 받는사이속도(0.75|1|1.35)
지향[]        아이디 · 이름(24자) · 진행
진행          단계번호 · 단 · 알 · 멈춘시각 · 이어감횟수
```

**저장하지 않는 것**: 사용자 식별자, 위치, 기기 정보, 기도 내용, 통계 전송. 08단계 검증에서 완주율을 재려면 사용자가 **직접 알려 주는 방식**을 쓴다 — 앱이 몰래 세지 않는다.

## 7. 이 문서가 07로 넘기는 것

07-b 목업은 **FR 번호를 화면에 매핑**해야 한다. 어느 요구사항이 어느 화면에서 충족되는지 대응이 없으면 목업은 그림일 뿐이다. 08 테스트 케이스도 같은 번호를 쓴다.

07-b 수용 기준(디자인 시스템 §9)에 한 줄을 더한다.
