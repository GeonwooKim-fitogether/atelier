# 2026-06 산출물 회수 — 최종 상태 (2026-08-27 갱신)

> 한 줄 요지: **회수는 git push로 끝났다.** 2026-08-27에 공방장이 로컬 작업 트리를 `recover/june-2026` 브랜치로 push했고, 그 브랜치를 3방향 병합해 6월 산출물이 바이트 단위로 저장소에 들어왔다. 이 폴더에는 그 전에 시도했던 실패한 회수 방법의 기록과, **아직 회수되지 않은 4개 파일**만 남는다.

## 왜 이 폴더가 있었나

2026-08-26에 6월 산출물이 Google Drive에만 있고 저장소에는 없다는 것을 발견했다. 그때 쓴 방법은 이랬다 — Drive 도구가 파일을 base64(바이트를 글자로 바꾼 표현)로 돌려주면, 그 글자열을 모델이 다시 타자해 파일로 쓰고 복원한다.

**이 방법은 조용히 파일을 망가뜨린다.** 언어 모델이 바이트 경로 안에 들어가기 때문이다. 실측 결과:

| 파일 크기 | 크기 검사 | UTF-8 검사 | 실제 상태 |
|---|---|---|---|
| 492 B · 496 B | 통과 | 통과 | 정상 |
| 1,931 B | 통과 | 통과 | **"프로젝트"가 "프로젅트"로 바뀜** |
| 1,600 B | 통과 | 실패 | 951번째 바이트 깨짐 |
| 1,984 B | 통과 | 통과 | **"4분면"이 "4북면"으로 바뀜** |
| 7,590 B · 16,348 B | 실패 | — | 크기부터 어긋남 |

가장 위험한 것은 세 번째 줄이다. **크기도 맞고 UTF-8도 유효한데 글자가 바뀌어 있다.** 자동 검사로는 잡히지 않는다.

## 어떻게 해결했나

git이 로컬과 클라우드를 잇는 유일한 통로라는 것을 확인하고, 공방장이 로컬 PC에서 다음을 실행했다.

```
git checkout -b recover/june-2026
git add -A
git commit -m "Recover 2026-06 working tree"
git push -u origin recover/june-2026
```

그 결과 88개 파일이 바이트 단위로 올라왔고, 클라우드 세션이 `git merge`로 합쳤다. 확인 근거 — `example-business-plan-my-rosary.html`이 전사 복원본에서는 16,351 바이트였는데 git 회수본은 **16,348 바이트**로 Drive 원본과 정확히 같다.

## 남겨 두는 교훈

**언어 모델을 바이트 경로에 넣지 않는다.** 파일을 옮기는 일은 git·rclone·curl처럼 바이트를 그대로 나르는 도구가 해야 한다. 모델이 base64를 다시 타자하는 방식은 크기 검사와 인코딩 검사를 모두 통과하면서도 글자를 바꿔 놓기 때문에, 검사를 아무리 붙여도 안전해지지 않는다.
